## Part 6: Wallet Transactions and Ledger at Join Time

**File:** `backend/app/services/wallet_service.py`

The wallet service creates `WalletTransaction` rows for each debit. Idempotency keys:
- `f"entry_deposit:{entry_id}"` for deposit portion
- `f"entry_referral:{entry_id}"` for referral portion (only when referral_amount > 0)

Each `WalletTransaction` row records: user_id, direction (DEBIT), type (TOURNAMENT_ENTRY), amount, balance_column (deposit or referral), idempotency_key, reference_id (entry UUID), description, meta (JSON with tournament details).

The idempotency key is stored with a `UNIQUE` constraint on `WalletTransaction`. Retrying a join with the same `entry_id` will fail with `DuplicateTransactionError` (409) rather than double-debiting.

For **refunds**, the keys follow the same pattern:
```
refund_deposit:<entry_uuid>     → credits deposit_balance
refund_referral:<entry_uuid>    → credits referral_balance (only if referral_amount_used > 0)
```

The same `UNIQUE` constraint on `WalletTransaction.idempotency_key` means retrying a cancellation after a partial failure will skip already-completed refunds without double-crediting.

### GAP 5: Idempotency Protection for Refunds

**Verdict: PRESENT — duplicate refund protection EXISTS ✅**

The wallet service uses deterministic idempotency keys:
```
refund_deposit:<entry_uuid>
refund_referral:<entry_uuid>
```

These are stored in `WalletTransaction.idempotency_key` with a UNIQUE constraint. A retry of the same cancellation will attempt to insert a `WalletTransaction` with the same key, which will fail with a `DuplicateTransactionError` (409 Conflict).

However, the current `cancel_tournament` code does NOT catch `DuplicateTransactionError` — a retry where the first refund succeeded but the second failed would cause the second retry to fail on the first refund's idempotency key. The existing code already flushes each entry's refund individually, but all within one transaction. If the transaction is rolled back and retried, the whole batch would be attempted again. Since all wallet writes happen before the DB commit, a commit failure rolls back all wallet writes too, making the whole operation retry-safe.

**The critical additional idempotency check for the post-release cancel path:** The `TournamentEntry.status` check (`status == EntryStatus.active`) in the refund loop means already-refunded entries (from a partial prior run) would be skipped. The existing refund loop only processes entries with `status == EntryStatus.active`:
```python
result = await db.execute(
    select(TournamentEntry).where(
        TournamentEntry.tournament_id == tournament_id,
        TournamentEntry.status == EntryStatus.active,
    )
)
```

This provides application-level idempotency: retrying after a partial failure will only refund entries that haven't been marked `refunded` yet.

**Conclusion:** Existing idempotency protections are sufficient for the post-release cancellation path — no new mechanisms are needed.
